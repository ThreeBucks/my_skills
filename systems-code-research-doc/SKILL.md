# 复杂系统源码调研文档

这个 skill 用于把复杂代码库、设计文档、历史讨论和当前代码证据，整理成可学习、可评审、可分享的技术说明。目标不是泛泛总结，而是讲清设计、主流程、关键权衡、证据来源和未验证点。

## 先路由

如果存在更窄的项目 skill，优先使用更窄的 skill：

- AdaEP/ACCL hang、mismatch、notify、dispatch、get_dispatch_layout、CI 失败或根因排查：优先用 `adaep-debugging`。
- AdaDnn CCL 架构、communicator、comm slot、rank_info、comm_id、AdaLink 或 collective 设计：优先读 `adadnn-ccl-dev`。
- Ada kernel 编写、tiling、编译、精度或测试生成：优先用对应 `ada-kernel-agent-skills` 子 skill。
- working-notes wiki 或 Obsidian 维护：优先用对应 wiki/Obsidian skill。
- 技术事实已经明确，只是在共创 proposal、PRD、RFC 或决策文档：优先用 `doc-coauthoring`。

如果用户同时要求“调研”和“写文档”，先做技术调研，再写文档。

## 输入

只收集目标输出所需的上下文：

- 目标仓库或目录。
- 设计文档、历史笔记、截图、日志或旧会话。
- 要解释的主题或子系统。
- 读者对象：自学、同事 onboarding、设计评审、分享材料。
- 深度：概览、架构、源码走读、性能/权衡分析、可执行实现指南。

如果读者或深度缺失，直接给出合理默认并简短说明。默认读者是“工程师 onboarding + 可分享技术笔记”。

## 证据流程

1. 建立来源清单。
   - 记录使用过的代码文件、文档、笔记、旧会话和外部资料。
   - 设计文档和历史笔记只代表意图；当前代码和测试才是实现事实。
   - 如果笔记和代码冲突，明确标出冲突，不要抹平。

2. 建立代码地图。
   - 找入口、公开 API、核心类/函数、device/runtime 边界、测试、示例、构建或启动脚本。
   - 保留短路径表，每个重要文件一句话说明职责。

3. 追踪主流程。
   - 从用户可见 API 或脚本，追到 runtime、kernel、transport、memory/buffer、输出和验证。
   - 系统代码要显式跟踪数据所有权、内存空间、同步点、rank/device 映射和生命周期。
   - 优先追真实调用链，不做宽泛目录总结。

4. 解释设计选择。
   - 区分“发生了什么”和“为什么这样设计”。
   - 点明约束：硬件拓扑、内存层级、API 兼容、性能、正确性、可调试性、迁移状态或历史包袱。
   - 如果代码规避了某些替代方案，说明原因。

5. 核验证据。
   - 关键结论要能回到文件路径、函数名、常量、测试、日志或命令输出。
   - 搜代码优先用 `rg`；如果有结构化解析工具，优先用结构化工具。
   - 除非用户要求执行，只做轻量验证。需要真卡、远端或大规模环境时，说明还需要在哪里验证。

6. 写交付物。
   - 结构匹配读者，不为了显得完整而堆章节。
   - 未解决问题和风险点要显式留下。
   - 最后给出下一步阅读、验证或实现建议。

## 输出形态

选择最小有用形态。

### 学习大纲

用户想学习一个代码库或子系统时使用：

```markdown
# 主题学习计划

## 目标
## 前置知识
## 阅读顺序
## 核心概念
## 源码走读
## 练习 / 待回答问题
## 未解问题
```

### 架构说明

需要解释设计和权衡时使用：

```markdown
# 主题架构说明

## 摘要
## 问题与约束
## 组件与职责
## 主流程
## 数据 / 内存 / 状态模型
## 关键设计决策
## 失败模式与调试入口
## 证据
## 未解问题
```

### 分享文档

输出给同事或用于分享时使用：

```markdown
# 主题

## 一句话结论
## 为什么需要它
## 心智模型
## 端到端流程
## 关键细节
## 为什么不是其他方案
## 需要注意什么
## 来源引用
```

## 质量标准

- 每个主要结论都能追溯到来源。
- 数据流复杂时优先用文字图或 Mermaid。
- 不粘贴大段代码，除非代码本身就是讲解对象。
- 没打开或没搜索过的代码不要描述。
- 不把生成笔记、过期文档或旧 assistant 输出当最终事实；要回到当前代码确认。
- 不过度贴合单次会话；写成未来 agent 或同事能接着用的材料。

## 最终回复

交付时包含：

- 交付物正文，或写入路径。
- 使用的证据来源。
- 做过的验证，以及没有验证的内容。
- 未解问题或建议继续阅读的位置。
