# 系统化调试

遵循 dev-baseline。先调查根因，后做针对性修复；把假设与观察分开。
调试授权不自动包含安装、生产探针、外部访问或大范围重构。

## 1. 定义异常与基线

- 读完整错误、堆栈和相关输出，记录时间、入口、输入及实际结果。
- 与用户描述的预期对照，确认不是一个相邻但不同的问题。
- 检查相关变更、配置、依赖版本和环境差异。
- 记录可用环境、已尝试步骤、失败频率及已知正常状态。
- 区分产品行为失败、测试装置失败、命令用错和环境不可用。
- 不把缺少工具或权限当作已证实的产品缺陷。

## 2. 建立最小反馈循环

优先选择能触达真实异常的最快可信方式：

- 行为测试：单元、集成或端到端，以实际边界为准。
- 命令或接口输入重放，比较输出与期望。
- 浏览器或客户端操作，检查可观察状态而非仅“未崩溃”。
- 捕获数据的离线重放、最小测试装置、差分或属性测试。
- 需要人工步骤时给出明确操作、期望、时间和应返回的证据。

只在授权范围内创建测试材料或运行探针，不自动保存规划和发现日志。
缩小输入、固定随机种子或时间、隔离外部状态，避免削掉触发条件。
对间歇问题记录样本数和失败率；一次未复现不能证明已修复。
压力实验有副作用与资源成本，先核对权限和范围。

### 环境不可用时

允许继续静态阅读、调用链分析、比较正常路径并列出可证伪假设。
明确标为“未复现 / 待验证”，不能声称动态确认了根因或修复。
说明需要的最小环境、日志、输入或访问条件；仅暂停依赖它的动作。
缺少运行条件不自动豁免 test-driven-development 的测试要求。

## 3. 追踪边界与差异

- 从错误值或异常状态逆向追到来源，再沿实际入口正向核对。
- 检查每个关键边界的输入、输出、配置传递和错误传播。
- 跟踪状态所有权、创建、修改、同步、释放与失效时机。
- 找同仓库正常路径，比较输入、不变量和调用顺序，不只比较代码外形。
- 测量性能问题的基线、工作量、噪声和资源条件，避免只靠日志推断速度。
- 只收集能区分假设的证据，不输出密钥或无必要的敏感数据。

## 4. 可证伪假设与实验

列出少量有依据的候选，按证据与验证成本排序，不固定数量。
每项写成：“若原因是 X，改变或观察 Y 应出现 Z；反例是 W。”

1. 选择最能区分候选的最小实验。
2. 一次只改变一个有解释力的变量。
3. 记录观察，与预测对照，更新或淘汰假设。
4. 没有新证据时不重复相同尝试，不叠加多个猜测补丁。
5. 探针本身可能改变时序或状态，必要时做无探针对照。

多次失败或修复不断引出新耦合时，重新检查问题模型和架构边界。
这只是重新评估的信号，不足以证明架构错误；新增重构走 design-workflow。

## 5. 修复与测试

- 在根因证据足够且实施获准后，选择最小源头修复，而非掩盖症状。
- 用 test-driven-development 建立先失败、再修复、后重构的循环。
- 测试应覆盖真实异常链路；不能只测一个不会暴露问题的薄辅助函数。
- 没有良好测试边界（seam）时，尝试更高层集成、重放或最小装置。
- 无好 seam 不自动豁免测试；无法合理建立时按 TDD 的显式例外规则处理。
- 复用已批准且覆盖本任务的例外，新增例外需确认，不逐文件重复问。
- 已实现后的回归敏感性检查不是补做 TDD，按 verification-before-completion 标注。
- 对外部或时序因素的容错也需要证据、明确范围和测试，不能笼统添加重试。

## 6. 核验与收尾

- 重跑原始场景与最小反馈循环，确认不是仅通过简化版用例。
- 检查相关回归及错误路径；性能结论保持同样的测量条件。
- 对本次临时探针说明位置和处理结果；仅在授权且来源明确时移除。
- 不删除用户已有诊断代码、数据、工作区或无关文件。
- 按 verification-before-completion 报告根因证据、修复、检查和剩余风险。
- 未复现、未运行、部分修复分别说明，不使用“应该没问题”代替结论。
- 不因调试结束自动提交、发布、安装依赖或清理其他资源。
