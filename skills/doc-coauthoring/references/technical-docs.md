# 技术文档的结构与表达

仅在需要组织技术事实、已定方案或教学材料时读取，不负责重新选择设计。

## 从读者动作选择结构

| 读者目的 | 最小有用结构 |
| --- | --- |
| 快速理解系统 | 一句话结论、边界、主流程、重要限制 |
| 学习与接手 | 前置概念、阅读顺序、接口、走读、练习或待验证问题 |
| 检查已定设计 | 目标与非目标、约束、已选方案、取舍、验收与风险 |
| 使用一个接口 | 前提、输入输出、最小示例、错误与生命周期约束 |
| 理解实现事实 | 版本、代码地图、调用与数据流、证据、未知项 |

模板是选择菜单，不是强制章节清单；删去没有实际内容的部分。
设计尚未确定时只表述候选和未知，将实质选择交给 design-workflow。

## 先主线，后细节

- 开头直接回答“是什么、解决什么、适用到哪里”。
- 每节围绕一个读者问题，标题能预告结论或内容。
- 先给整体入口到结果的过程，再解释关键分支、失败路径和限制。
- 文件、函数、类型和状态名保持与源材料一致，别凭空改名。
- 术语首次出现给定义；缩写不能替代解释。
- 区分逻辑模块、部署单元、执行主体和数据对象，避免混为一个层级。
- 示例最小可理解，标明示意、可执行与未验证状态，不编造运行结果。
- 不大段粘贴源码；只有代码本身是分析对象时保留必要上下文。

## 工程师口吻

- 先写结论、机制和约束，不用“下面将详细介绍”等开场或过程叙述。
- 用具体主语和动作：谁调用、谁持有、何时生效、失败由谁处理。准确术语比堆砌术语重要。
- 一段解决一个问题，长段落按因果拆分；并列步骤用列表，对照用表格，不把连续推理拆成碎片。
- 删除无信息增量的优势、重复总结、夸张评价。“高效、灵活、可靠”必须落到机制、条件或数据，否则删掉。
- 检索过程、工具调用与自查过程不塞进正文；必要验证信息放简短交付说明，来源仍紧邻技术主张。
- 简洁不能删去接口契约、失败路径、适用范围或不确定性；不设机械字数限制，不刻意口语化。

示例仅展示表达方式，不是当前项目事实：

> 避免：通过统一资源管理实现全面管控，有效提升系统可靠性与可维护性。
>
> 改为：资源由 Session 持有。请求结束后归还，Session 关闭时统一释放。调用方不直接释放底层资源，避免重复释放。

## 事实、决策、推断与提案

- **事实**：在指定版本、条件下由源或运行观察支持。
- **决策**：已被选择的方案及已记录理由，不保证已经实现。
- **推断**：依据已观察内容推导，说明关键假设与不确定性。
- **提案**：未来可能改变的内容，使用明确的未来语态和边界。

“现状如此”与“建议如此”不要混在同一描述里。
性能、安全性和可靠性主张必须注明支持条件；没有测量不要写确定数字。
设计材料与实现冲突时并列说明，不为了文风统一而删去冲突。

## 表格、代码与图

- 比较或枚举适合表格；时序、依赖和生命周期适合图。
- 图数量由表达需要决定，相关要求见 [diagrams](diagrams.md)。
- 每张图附近有解释它能回答什么问题的图注，而非重复标题。
- 表格空格或图中虚线不能代替“未知”；明确写出未知语义。
- 关键结论的引用紧邻主张，避免只在文末堆一串无法对应的链接。
- 引用应能定位到版本、路径、符号或章节；核对目标实际存在与可访问性。

## 局部编辑与交付检查

修改前读当前文件，保护用户编辑；以最小替换消除错误和冗余。
跨节检查术语、版本、方向、接口、状态与图文一致性。
按 [reader-check](reader-check.md) 检查读者是否不靠会话即可理解。
正式文档可以按要求落盘；大纲选择、脑暴和过程状态默认留在会话。
交付标明正文位置、来源范围、完成检查及未验证内容，不自动发布。
