# 技术图：先语义，再视觉

起草设计文档时主动评估哪些模块和流程用图更直观，不等待用户点名要图。每图必须有明确读者问题和源依据，不限定图数。
语义正确与视觉可读是两个独立检查；渲染成功不证明关系正确。

## 表达方式选择

| 要解释的内容 | 优先考虑 |
| --- | --- |
| 模块职责、依赖与系统边界 | 组件关系图 |
| 多模块交互、异步完成与同步 | 时序图 |
| 初始化、运行、失败、释放与复用 | 状态或生命周期图 |
| 数据归属、布局、读写关系 | 数据/内存示意图 |
| 新旧方案的结构变化 | before/after 对照图 |
| 参数、能力或方案优缺点 | 表格 |
| 单一判断或简单规则 | 短文字 |

有明显收益就按既定文档目标配图；不额外创建远端目标，不自动安装工具或扩大写入范围。
图应替代难懂的文字，图后只解释关键路径、约束和易误读点；不逐框重复正文。
已有图足够时复用，不因“主动选图”重新绘制；用户明确要求纯文字时遵守。

## 1. 先确定图的意图

- 写明要表达的系统边界、时间范围、版本与抽象层次。
- 选择合适形式：组件关系、数据流、调用时序或状态生命周期。
- 不把所有视角塞进同一图；拆图取决于歧义和可读性，不是配额。
- 明确现状、已定但未实现的设计与探索提案，分图或用图例区分。
- 用户已定设计不因绘图而重开；发现矛盾先报告，不自行补造结构。

## 2. 建立节点与关系清单

新建图或改变节点关系时，先在会话中列清单，再生成图源码；不自动创建额外规划文件。
纯图注、措辞修改复用已有结构，仅核验受影响部分。

- **节点**：名称、类型、职责、证据位置、是否在图边界内。
- **关系**：源、目标、方向、含义、触发条件、依据。
- **边界**：进程、组件或信任边界，以及跨边界的具体动作。
- **状态**：初始状态、合法迁移、触发事件、终止状态与资源归属。

节点同名不代表同实例；同一逻辑对象跨图应保持名称一致。
聚合节点须说明折叠了什么，避免隐藏关键中间责任或必需边。
未知关系标为未知，不为了图完整而发明连接。

## 3. 方向和类型不能混淆

- 调用箭头通常从调用者指向被调用者，返回值需另标或说明。
- 数据箭头从生产者指向消费者，名称说明载荷或状态，不只写“交互”。
- 依赖箭头方向须在图例定义，不能让读者猜“依赖于”还是“被使用”。
- 控制流与数据流采用可区分的线型或标签，颜色不能是唯一标识。
- 请求与响应不因为往返而默认双向箭头；两个方向各有含义才各自画出。
- 生命周期图显式给出创建、初始化、运行、失败或取消、释放等适用阶段。
- 状态迁移边标明事件或条件；不要把状态名与执行动作混成同类节点。
- 时序图检查发送者、接收者、因果顺序、并行段与同步点。
- 拥有、引用、复制与借用不同；标明资源由谁负责释放。

## 4. 图注与证据

每图附近提供：

1. 它回答的问题与适用范围。
2. 节点类别、箭头方向和线型含义。
3. 省略的细节、假设、未知或提案标记。
4. 关键关系的源路径、符号、版本或已定设计依据。

图注应使图可以脱离作者口头解释被阅读。
无障碍文本应概述关键关系，不只重复“架构图”。

## 5. 语义审查（semantic）

对照实际需求、源与最终节点结构逐项检查：

- 必需节点、边、方向、状态、错误路径是否完整？
- 有无凭空添加、关系倒置、重复节点或未解占位？
- 控制和数据是否被错误混合，状态迁移是否可达？
- 图与正文及其他图是否使用同样术语和约束？
- 现状与提案是否会被误读？

独立审查不依赖作者自评或另一位评审的通过结论。
需要的源或最终产物不可直接检查时，语义状态为未验证，不能判定通过，列明具体缺口。
只有实际检查发现不符合要求时才标记失败。

## 6. 目标渲染与视觉审查（visual）

在实际交付格式和目标渲染器中检查，而非只看源代码能否解析。
检查字号、对比度、边标签、箭头端点、交叉线、裁切、分组和阅读顺序。
按预期展示尺寸检查，不以放大后可读代替常规尺寸可读。
需要导出时检查导出后的文件；源视图正常不证明导出正常。
无法渲染或查看则说明视觉未验证，不把语义通过写成图已全面通过。
修改节点或边后重做受影响语义审查；纯布局修改仍要检查方向没有误变。

## 7. 内部信息与工具

- 禁止将内部图源码、截图或材料上传公共在线编辑器或渲染服务。
- 内部图不得依赖公共 CDN 的脚本、字体或样式；使用可信本地或内部资源。
- 使用已授权工具，不能因缺少渲染器就自动安装或切换外发服务。
- 不在外部 URL、日志或错误上报中携带内部内容。
- 本地正式图稿按交付授权保存；对外发送和发布需另有对应授权。
