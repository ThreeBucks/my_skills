# 文档共创与技术表达

遵循 dev-baseline。把事实、已定方案和必要背景转成读者能独立理解的材料。
不将写作请求自动扩大成方案重选、代码实现、无限检索或外部发布。

## 1. 选择最短写作路径

- 用户要完整初稿且材料足够：直接起草并自查，不强制访谈或逐章批准。
- 用户要迭代共创：按问题收集、结构与正文、读者检查推进。
- 用户要源码调研：先取证，再形成技术说明，不能先编结论再找支撑。
- 已有设计直接表达；只有实质未决方案才按需交给 design-workflow。
- 写作中发现事实与设计冲突，标出证据和影响，不自行变更已定设计。
- 用户明确跳过某个可选阶段时遵守，不重复索取该选择。

## 2. 建立写作契约

先复用请求和材料中已有答案，只有重要缺口才询问：

- 读者是谁，读完应理解或决定什么？
- 是概览、教程、技术走读、提案还是正式说明？
- 现有模板、深度、篇幅、语言和交付格式是什么？
- 哪些内容是已确认事实、已定决策、待验证假设或候选提案？
- 可读的来源、可写的文件和可发布的目标分别有哪些？

默认规划留在会话与 todo，不自动写 plan/spec/progress/findings。
用户明确要求的正式文档和配图可交付文件，但不附带一套过程材料。
只读审阅仅给建议；本地文档授权不自动覆盖连接源搜索或外部写入。

## 3. 按需取证

需要源码和复杂系统说明时读 [source-research](references/source-research.md)。

- 建立最小来源清单，区分当前代码、测试、日志、设计和历史讨论。
- 从真实入口沿主流程追踪到结果，不写泛泛目录介绍。
- 关注接口、调用关系、控制与数据、状态所有权和生命周期。
- 每个关键结论关联路径、符号、版本、命令或文档位置。
- 没有直接查看的实现不描述为已证实；旧材料与当前事实冲突应显式说明。
- “实现做了什么”与“为什么这样设计”分开，后者缺依据则标为推断。
- 仅在请求授权范围内运行验证；不可用环境标为未验证。

## 4. 组织与写作

技术说明按需读 [technical-docs](references/technical-docs.md)。

- 以读者问题组织结构：结论、必要背景、主流程、关键细节、限制与来源。
- 用具体主语与动作写清谁负责、何时生效、失败如何处理；一段解决一个问题，长段落按因果拆分，不机械变成碎片列表。
- 删除空泛优势、套话、重复总结和过程自述；“更高效/可靠”等判断要有机制、条件或数据。简洁不能省掉接口约束与失败路径。
- 正文讲主线，表格承载对照，附录容纳必要细节，不为完整感堆章节。
- 术语首现给定义，后文保持一致；代码片段只保留讲解所需部分。
- 保留重要约束、失败路径和不确定性，不用流畅叙事抹平证据冲突。
- 实际观察、静态推导和未来提案明确标注，不能混写为现状。
- 共创时围绕真实反馈局部修改，不要求用户按固定数量挑选段落。
- 用户直接编辑后先读当前内容，保护其修改，再做定向编辑。
- 重要未解问题可列入草稿，但不能把关键缺失隐藏为“完整交付”。

## 5. 配图与目标渲染

起草设计文档时，主动评估模块关系、关键流程、状态和数据模型是否更适合用图表达。
图能明显降低理解成本时，在既定交付范围内主动配图，不等待用户额外要求。
简单结论保留文字，比较与枚举优先考虑表格；不固定图数，不用图重复正文。
新建图或改变关系时读 [diagrams](references/diagrams.md)；纯图注修改复用已有结构。

- 先核对节点、边、方向和语义，再优化布局与颜色。
- 明确控制流、数据流、依赖、状态迁移与生命周期，避免一条箭头多种含义。
- 现状与提案分图或显式区分；不能把设想渲染成已实现关系。
- 每图配图注、图例、范围与必要的来源或假设说明。
- 在实际目标格式或渲染器检查，而非仅看源文本语法。
- 语义审查（semantic）与视觉审查（visual）分开记录，互不替代。
- 无法目标渲染或直接查看时，明确未验证，不宣称图已通过。
- 内部材料不得上传公共图编辑器，不用公共 CDN 渲染内部图或载入其资源。
- 只用已授权且可信的本地或内部工具，不自动安装或外发数据。

## 6. 读者检查与事实回查

按需读 [reader-check](references/reader-check.md)。

- 从读者任务提出少量真实问题，不用固定配额。
- 检查读者能否仅凭文档找到主张、流程、约束、例外和依据。
- 可用且获准时请独立读者或代理检查，不给作者预设结论。
- 未使用独立读者时如实称自查，不伪称独立验证。
- 读者理解正确不代表技术事实正确，关键主张仍需回查来源。
- 发现误读时修正文档，再检查受影响问题与图文一致性。

## 7. 交付

用 verification-before-completion 核对正文、引用、图、格式和用户要求。
交付正文或文件路径，并说明来源范围、实际检查、未解问题和未验证项。
正式文档完成不自动授权发布；复用已有发布授权但不扩大对象、目标和范围。
