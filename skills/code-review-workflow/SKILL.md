# 代码评审工作流

遵循 dev-baseline。先确定模式；评审建议不是写入或发布授权。
以需求、当前代码与证据为准，不盲信实现者、其他评审者或自己的旧结论。

## 1. 确定模式与范围

- **发起**：组织评审材料，选择合适的独立评审方式。
- **执行**：只读检查实际产物，给出可定位、可行动的发现。
- **接收**：验证反馈，采纳、澄清或用证据反驳，再做获准修正。
- 读当前请求、项目约束、已批准设计与验收，不要求另建计划文件。
- 明确目标分支、基线、变更集合、排除项和当前工作区状态。
- 提交范围从任务与历史确认，不默认把 HEAD~1 当正确基线。

工作区评审至少检查：

- 已提交且属于任务的差异（适用时）。
- 未暂存的改动以及已暂存的改动。
- 相关未跟踪文件（untracked），包括新增测试、配置和文档。
- 与改动相关的调用者、被调用者、类型契约和测试，而非仅 diff 行。

用户明确只审某范围时遵守；发现遗漏风险可提示，不擅自扩大写入范围。
无法读取相关源或产物时报告评审缺口，不能凭摘要判通过。

## 2. 发起模式

提供自包含的最小评审材料：

1. 需求、已定设计、非目标和验收标准。
2. 当前产物位置、具体 diff 范围和未提交内容的获取方式。
3. 相关项目约束、已知基线失败和重要风险。
4. 已运行检查的实际输出，以及明确的未验证项。
5. 只读权限、允许的检查及返回格式。

- 不以实现者声称“全完成”“测试全绿”诱导评审者结论。
- 评审者应直接检查源与产物，而非只验证总结措辞。
- 隔离工作区可能看不到未提交内容，须确认评审对象与实际交付一致。
- 风险和宿主要求决定是否委派，不强制固定数量或固定模型。
- 不默认对外发送评审材料或创建远端评论。

## 3. 执行模式

先核对需求符合性，再检查代码质量；可在同一轮进行。

- 是否遗漏需求、添加未授权行为，或改变已定接口与兼容性？
- 数据和控制路径是否真实可达，边界、空值、错误路径是否正确？
- 状态所有权、同步、资源释放、取消与重试是否符合契约？
- 是否存在安全、数据损坏、性能回退或可维护性风险？
- 是否在正确职责边界完整解决问题，是否引入越层依赖、散落特判、重复状态或不必要的重构范围？按 dev-baseline 的整体性原则检查。
- 架构异议须指出具体依赖、契约、维护成本或错误风险及必要修正边界；不能仅凭“不够优雅”阻塞交付。
- 测试是否覆盖真实行为和失败模式，而非只验证模拟或实现细节？
- 文档、配置、生成物与当前实现是否一致？

按严重性先报问题，最后再总结。每项包含：

- 位置：文件与最小相关行区间或符号。
- 触发条件与用户可见影响。
- 代码、测试或可重现证据及必要推理。
- 建议方向；不把个人风格偏好包装成阻塞缺陷。

证据不足的担忧标为疑问，不能编造复现、测试结果或确定性。
无发现时说“在该范围未发现问题”，并列出验证限制，不宣称没有缺陷。

## 4. 接收模式

- 完整读取反馈，再对照需求、当前代码、历史决策与运行证据核实。
- 不为礼貌盲目同意，不为自我辩护拒绝正确意见。
- 可确认且在授权范围内的项，按风险与依赖顺序逐项修正、测试。
- 某项不清楚时仅暂停依赖它的部分，继续独立且明确的授权修正。
- 建议新增行为、公共接口或大范围重构时，仅为新增部分请求确认。
- 反馈与既有批准冲突时展示冲突与证据，不悄悄推翻决定。

有证据反驳时说明：原主张、当前事实、代码或测试依据，以及结论。
例如：“此路径仍有调用者，位置为 X；删除会破坏 Y，建议保留并修正 Z。”
无法验证则明确缺什么，不能把“暂不接受”表述成已证伪。
自己反驳错误时直接更正事实，继续范围内处理。

## 5. 收敛与交付

- 修正后复查受影响路径与相关测试，不靠“已改”自动关闭问题。
- 记录每项状态：已修复、证据反驳、待澄清、未验证或明确接受的风险。
- 阻塞问题未解时不宣称可合并；独立工作不必无条件停下。
- 以 verification-before-completion 复核当前状态和逐项需求。
- 交付评审范围、问题清单、验证和剩余风险，不默认 commit、push 或外发评论。
