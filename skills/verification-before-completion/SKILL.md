# 完成前验证

遵循 dev-baseline。证据先于结论；只宣称证据实际覆盖的结果和范围。
本入口核验完成状态，不把事后检查重新命名为测试驱动开发。

## 1. 明确需要证明的主张

- 重新读取当前请求、已批准方案、验收与明确排除项。
- 在会话或 todo 中逐项映射“需求 → 产物 → 检查 → 结果”。
- 检查行为之外的要求：文件位置、接口兼容、文档、权限和副作用。
- 确认当前分支、相关 diff、暂存及相关未跟踪文件，别漏掉未提交产物。
- 代理总结、计划打勾或自己认为完成，都不是独立的完成证据。

## 2. 运行检查或复用有效证据

已有证据可复用，但必须同时满足：

- 确实取得并读过检查输出、退出码和关键断言。
- 与当前相关代码、配置、依赖、输入和环境一致。
- 覆盖当前要做的主张，没有未解失败或新疑点使其失效。
- 能说明检查范围和来源，不仅是一句历史“通过”。

换会话、换阶段、加载技能或发送进度不必机械重跑。
相关内容改变、集成后状态不同或出现新风险时，重跑或补充受影响检查。
不能证明旧证据仍适用时，重新验证或标记未验证。

## 3. 选择与主张匹配的检查

| 要宣称的内容 | 至少需要的证据 |
| --- | --- |
| 某些测试通过 | 该范围的实际输出、退出码、失败与跳过情况 |
| 构建成功 | 对应构建命令及产物结果，不能只用格式或静态检查 |
| 缺陷修复 | 原始异常场景的有效验证及相关回归 |
| 性能改善 | 可比输入、条件、基线、测量与噪声说明 |
| 文档可信 | 关键事实来源、引用和读者问题检查 |
| 图可交付 | 节点关系语义核对和目标渲染视觉检查 |
| 需求完成 | 每项需求与产物、证据之间的对应关系 |

按风险选最小但可信的组合，不用局部测试冒充全量覆盖。
没有测试适用的纯文档任务做结构、语义、链接和目标格式检查。
源代码被修改不证明行为已变正确，命令已运行也不证明成功。

## 4. 读取和分类结果

- 检查关键输出、退出码、失败数、跳过项、警告和环境条件。
- **通过**：证据直接支持指定范围的主张。
- **失败**：检查确实执行，并观察到不满足预期的结果。
- **未验证**：缺环境、权限、输入或未运行，无法得出产品行为结论。
- **不适用**：说明为何该检查与本次产物无关，不冒充通过。
- 区分既有基线问题、本次回归、测试装置和环境故障。
- 可在授权范围修复普通失败；涉及新范围时仅暂停依赖部分。
- 缺环境不等于产品失败，但也不能当作检查通过或功能已修复。

## 5. 回归测试敏感性（按需）

事后补测可用“有修复通过、去掉修复失败、恢复后通过”检查是否能抓住缺陷。
这叫回归敏感性检查，不是 TDD；TDD 顺序由 test-driven-development 规定。

- 优先在安全副本中比较，或只操作可明确隔离的本任务改动范围。
- 先确认原始状态、改动来源、恢复方式和授权，保护未提交的用户工作。
- 不重置整个工作区、覆盖共享文件或删除用户代码来制造失败。
- 只撤销目标修复，确认失败原因正是目标缺陷，而非副本环境失效。
- 恢复后核对文件状态，并重跑确认；不能留下实验状态当最终结果。
- 无法安全隔离则不做撤销实验，报告敏感性未验证及替代证据。

## 6. 对委派与集成结果复核

- 直接核对实际 diff、产物和证据，不仅接收“完成”状态。
- 确认检查对象正是将交付的文件版本，包含相关未提交内容。
- 检查组合后的接口、共享状态和依赖，单项通过不保证集成通过。
- 必需源或产物无法直接检查时，报告具体缺口，不推断评审通过。
- 语义与视觉、事实与表达、需求与测试分别核对，不互相替代。

## 7. 交付、发布与清理

- 默认交付本地结果、变化摘要、实际检查和风险，不主动要求选择发布菜单。
- 提交、安装、推送、合并、发布和清理均需对应授权，不从测试通过推导。
- 执行已授权发布前核实目标、产物版本、来源与项目明确的发布条件。
- 已选择且获准的交付方式持续有效；目标或范围改变才确认新增部分。
- 清理先证明对象来源、所有权和本任务关联，目录名称不构成证明。
- 不删除宿主管理、用户原有或来源不明的工作区、分支与文件。
- 破坏性丢弃需明确对应对象的授权；没有清理请求时保留结果。

## 8. 最终表达

先给实际状态，再列改动、检查命令或方法、覆盖范围与剩余风险。
逐项未满足就如实报告部分完成；不要以“看起来”“应该”暗示已通过。
只把当前有效证据支持的事项标为完成，不隐去失败、跳过与未验证项。
