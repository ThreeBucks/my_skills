# 设计工作流

本入口负责决定“做什么、为什么、边界是什么、如何验收”。
遵循 dev-baseline；不把写文档或启动实现作为设计的必经动作。

## 1. 确认设计是否尚未决定

- 先读请求、相关代码、项目约束、历史决策和已有批准。
- 会话中的明确方案有效，不要求先有 spec 或正式计划文件。
- 已批准内容不重新竞选方案，不因保存、续接或技能切换重复审批。
- 仅写已定方案的说明文档时，转 doc-coauthoring，不重开设计。
- 请求只是阅读、定位或评审时，不把它扩大成改造项目。
- 用户只要建议时停在建议；实施须有相应授权。

## 2. 建立问题与验收

用最短形式列出以下内容，缺项先查现有上下文：

- 目标：用户需要改变的可观察行为或解决的问题。
- 现状：相关入口、依赖、实际瓶颈与已有证据。
- 约束：兼容性、性能、安全、可维护性、时间和权限。
- 非目标：明确本轮不做什么，防止顺手扩大范围。
- 验收：输入、输出、边界情况和可执行或可检查的成功条件。
- 未知：哪些是假设，哪些需要测量、用户决策或补充材料。

只询问实质影响方案或授权的未解问题，不为流程凑问题。
不影响目标的可逆细节沿用项目惯例，并说明重要假设。
等待关键答案时可继续独立且已授权的调查。

## 3. 比较最小有用方案

- 有真实选择时比较少量候选；没有实质差异时不虚构备选。
- 先给推荐方案，再给理由、代价、风险和放弃其他方案的原因。
- 以现有实现为基准，说明保留现状能否满足目标。
- 评估变更面、依赖、迁移成本、故障模式和测试可达性。
- 局部补丁若增加重复逻辑或跨越职责边界，比较边界内的结构性修正；收益不足以支撑扩大范围时保留现状，不为优雅启动全局重构。
- 不用抽象层数、文件数量或“更专业”代替实际收益。
- 不为猜测的未来需求引入框架、配置项或扩展点。
- 性能结论依赖测量；没有测量时标为预测并说明验证方法。

## 4. 架构与重构评估

沿真实调用链检查，而不是机械按目录层级划分责任。

- 模块是否把复杂行为隐藏在小而稳定的接口之后？
- 调用者必须知道哪些类型、不变量、时序、错误和配置？
- 一处变化是否需要修改多个调用者，状态所有权是否清楚？
- 删除一个薄包装层会消除复杂性，还是把必要逻辑散落出去？
- 测试边界是否覆盖真实调用方式，而非只测孤立的辅助函数？
- 是否可以利用现有边界解决问题，避免只为测试制造公共接口？
- 错误传播、资源释放、并发和生命周期是否与接口约定一致？

每个值得推进的候选说明：位置、可观察问题、建议边界、收益与风险。
若与既有决策冲突，列出新证据；不能静默推翻已定决策。
没有充分证据的候选标为探索项，不当作必须实施的任务。

## 5. 收敛与确认

按任务大小表达方案：简单任务几句话，复杂任务分解为可验收单元。
会话或 todo 即可，不自动写 plan、spec 或决策记录。

收敛内容至少包括：

1. 已选方案及关键取舍。
2. 组件职责、重要接口、数据或状态流向。
3. 兼容、错误处理和迁移边界。
4. 预期文件影响面与不允许触碰的区域。
5. 验收条件、验证方式和仍需补证的事项。

只对尚未批准的实质内容请求确认；既有授权持续有效。
对用户明确要求的阶段审阅保留该条件，不把沉默当批准。
正式设计文档或配图被明确要求时，由 doc-coauthoring 负责表达与交付。

## 6. 交接

- 实施已授权：将已选方案、边界和验收交给 execute-work。
- 实施未授权：交付设计结论和待决定事项，不写实现代码。
- 调查揭示真实异常：按需使用 systematic-debugging 取证。
- 架构结论改变已批准范围：只暂停和确认受影响部分。
- 不自动创建工作区、安装依赖、提交文件或发布文档。
- 完成设计不等于实现已完成，也不等于文档已通过事实核验。
