# 测试驱动开发

遵循 dev-baseline。本入口独立规定红—绿—重构；其他流程引用它而不另造例外。
核心顺序：先写行为测试并观察预期失败，再写最小实现，最后保绿重构。

## 1. 适用范围与例外

- 新增行为、修复缺陷和行为调整，默认先建立可观察的失败测试。
- 纯重构先确认既有行为测试通过，覆盖缺口先补表征测试，再保绿重构。
- 不为无行为变化的重构故意破坏代码制造红灯。
- 纯文档、说明性配图或措辞修改不机械套单元测试，应做结构、事实与阅读核验。
- 可执行脚本、代码生成器和会改变行为的配置不能仅因文件类型自动豁免。
- 原型、生成物或特殊环境需要偏离时，说明原因、范围、风险和替代检查。
- 新增例外需明确授权；普通实施批准不是跳过测试的批准。
- 已批准且仍覆盖当前任务与影响面的例外可复用，不逐文件或续接重复确认。
- 没有测试框架、没有良好 seam、时间紧或环境缺失都不是自动例外。
- 无法运行时可准备测试和分析，但不得声称观察到红绿或已完成 TDD。

## 2. 定义一个行为

- 从需求和用户可见结果写预期，不从刚写好的实现复制细节。
- 一次一个可理解的行为，测试名说明输入条件与应有结果。
- 选择覆盖真实调用方式的边界；缺陷跨多个调用者时不能只测一个孤立函数。
- 尽量使用真实逻辑和轻量数据；仅在外部边界不可避免时使用替身。
- 替身不能成为断言的唯一对象，不要只验证它按配置返回。
- 断言应区分正确与错误行为，不只检查对象存在或过程没崩溃。
- 必要边界包括错误输入、失败传播、状态迁移与资源生命周期。

## 3. 红：先写并运行失败测试

1. 添加最小测试，保持生产实现不变。
2. 用项目适用命令运行该测试，读取输出和退出码。
3. 确认失败来自目标行为缺失或缺陷，而不是拼写、环境或测试装置错误。
4. 必需的新接口缺失可体现预期红灯，但先排除加载路径或无关依赖错误。
5. 测试意外通过时，检查是否已有该行为、断言无效或输入未触达问题。
6. 修正测试直到它对目标缺陷产生可信的失败信号。

将命令、关键断言和失败原因保留在会话或 todo 中，不自动写过程日志文件。
只有确实看到预期红灯，才能说该轮已完成“红”。

## 4. 绿：最小实现

- 实施满足当前行为的最小改动，不顺带扩展功能或重构周边。
- 运行同一测试，检查退出码、断言和异常输出。
- 失败时修实现；不能削弱正确断言来迁就错误行为。
- 若需求或测试本身确有错误，先说明证据，再修正它，不偷换验收。
- 运行相关回归；新失败需要定位，不能只报告目标测试绿灯。
- 警告和已有失败按来源说明，不把任何输出都笼统算成产品失败。

## 5. 重构：保持绿色

- 仅在目标测试和适用回归通过后整理结构、命名和重复逻辑。
- 不新增行为；下一项行为重新从红开始。
- 每个有风险的整理后运行相关测试，保持可定位性。
- 不为测试暴露生产专用后门或添加只供测试调用的公共接口。
- 难以测试时先检查接口和边界；必要架构改变仍遵守授权范围。

## 6. 如果实现已经写在测试之前

- 如实标记顺序缺口，不能把后来通过的测试称为先红后绿。
- 不删除用户代码、原有改动、无关文件，也不重置整个共享文件。
- 若能安全区分并重建自己本次实现，可在获准范围内隔离或撤销这部分后重新循环。
- 无法安全隔离时保留工作，说明缺口并请求适用的例外或处理决定。
- 单纯撤销修复看测试失败、再恢复，只是回归敏感性检查，不会追溯变成 TDD。
- 此类检查的安全副本、边界和证据要求由 verification-before-completion 规定。

## 7. 卡住时

- 测试装置太大：尝试真实的更高层边界、最小重放或更小输入。
- 必须模拟一切：检查是否测错边界，别只验证自己的模拟。
- 缺少运行环境：说明需要的最小条件，继续不依赖它的授权工作。
- 无法覆盖真实缺陷：明确记录风险，不以“没有 seam”宣称免测。
- 例外获准后执行替代检查，并在交付时保留未验证范围。

## 8. 完成前

- 对每项行为指出测试、红灯证据、绿灯证据与相关回归范围。
- 区分真正 TDD、已有行为表征、事后补测和授权例外。
- 用 verification-before-completion 核验当前状态，复用仍有效的证据。
- 通过一个测试不等于所有需求完成；无环境不等于产品失败，也不等于通过。
